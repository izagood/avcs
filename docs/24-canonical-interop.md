# 24 — 정규 직렬화의 상호운용 계약

avcs 객체의 정체성은 **정규 바이트의 sha256**이다. 그래서 정규화가 구현마다 갈리면 같은 내용이
다른 oid를 받고, **오류 없이 수렴하지 않는다** — 서버는 가진 것을 정직하게 답하고 클라이언트는
없는 것을 정직하게 요청하는데 영원히 만나지 않는다. 프로토콜에서 가장 진단하기 어려운 실패다.

이 문서는 그 정규화를 **언어 중립으로** 고정한다. 다른 언어로 avcs 호환 서버나 클라이언트를
만들려면 이것과 `spec/canonical-vectors.json`이 계약이다.

## 1. 형태

```
oid = "<type>_" + sha256("<type> " + canonical(payload)).slice(0, 32)
```

- 해시 입력은 정규 JSON 앞에 **타입과 공백 한 칸**을 붙인 것이다. 같은 페이로드가 다른
  타입으로 재해석되어 같은 주소를 받는 것을 막는다. (이 접두사가 이 문서의 첫 판에는
  빠져 있었다 — 첫 비-JS 구현이 골든 벡터로 잡았다. 벡터가 문서보다 강한 이유다.)
- `canonical`은 **JSON**이다. 저장 형식은 자유다 — 참조 구현은 CBOR로 저장하지만 oid는 JSON
  파생이고, 와이어도 JSON이다. 이 분리가 의도된 것이다: 저장을 바꿔도 oid가 안 바뀐다.
- `<type>`은 페이로드의 `type` 필드가 아니라 **별도 인자**다. 페이로드에 `type`이 함께 있어도
  접두사는 인자에서 온다.
- `oid` 필드와 `sig` 필드는 해시 대상에서 **제외**된다 — oid는 내용의 고정점이어야 하고,
  서명은 oid를 서명하므로 자기가 서명하는 것 안에 있을 수 없다.

## 2. 정규 JSON

| | 규칙 |
|---|---|
| 공백 | 삽입 공백 없음 |
| 객체 키 순서 | **코드포인트 오름차순** |
| `undefined` 필드 | 탈락(객체에서만) |
| 배열 | 순서 보존, `undefined` 원소는 `null` |
| 수 | 정수만, `±(2^53-1)` 이내 |
| `true`/`false`/`null` | 소문자 리터럴 |
| 문자열 이스케이프 | JSON 필수만 — `\"` `\\` `\n` `\r` `\t`, 그리고 `U+0000`–`U+001F`의 `\u00XX`. 나머지는 **UTF-8 그대로** |

키 정렬의 함정: `"알파벳 순"`이 아니다. 코드포인트 순이므로

```
"10"(0x31) < "A"(0x41) < "_c"(0x5F) < "a"(0x61) < "b"(0x62)
```

대문자가 소문자보다 **앞**이고 밑줄이 그 사이다. 대소문자 무시 정렬로 구현하면 `A`와 `a`가
뒤집힌다.

비-ASCII 값의 함정: 이스케이프하지 **않는다**. `"한글"`을 `"한글"`으로 쓰는 구현은 다른
바이트, 따라서 다른 oid를 낸다.

## 3. 상호운용 안전 부분집합

정규 규칙만으로는 부족하다. ECMAScript 고유 동작 셋이 남아 있어 다른 언어에서 갈릴 수 있고,
그래서 애초에 **그런 값을 허용하지 않는다.** `assertInteropSafe`가 강제한다.

### 3-1. 수 — 정수만

`JSON.stringify(n)`은 ECMAScript `Number::toString`이다. `1.0`은 `"1"`로, `1e21`은 `"1e+21"`로
쓴다. Python `repr`도 Go `strconv`도 모든 경우에 이것과 일치하지 않는다.

부동소수를 허용하면 그 표기를 명세로 옮겨야 하고, 그건 ECMAScript 명세를 그대로 베끼는 일이다.
대신 **정수만** 허용한다. 정수의 십진 표기는 언어를 넘어 같다.

`±(2^53-1)`을 넘는 정수도 거부한다 — 배정도에서 정확히 표현되지 않는다.

### 3-2. 객체 키 — astral 금지

`Array.prototype.sort`는 **UTF-16 코드유닛**을 비교한다. astral 문자(`U+10000` 이상)는
surrogate pair로 표현되고 상위 surrogate(`U+D800`–`U+DBFF`)는 `U+E000`보다 **작다**. 그래서
UTF-16 정렬은 astral 문자를 `U+E000`–`U+FFFF` **앞**에 두고, 코드포인트 정렬은 **뒤**에 둔다.
같은 객체, 두 순서.

BMP 안에서는 두 정렬이 **일치한다.** 그래서 astral 키를 거부하면 정렬 규칙을 "코드포인트 순"
하나로 단정할 수 있고, UTF-16 기반 언어와 코드포인트 기반 언어가 같은 답을 낸다.

**값에는 이 제약이 없다.** 값은 정렬에 참여하지 않으므로 `"배포 완료 🚀"`나 `"docs/이름.md"`는
그대로 허용된다.

### 3-3. 객체 키 — NFC 필수

같은 글자의 두 유니코드 표현(`é` = `U+00E9` vs `e`+`U+0301`)은 다른 바이트이고 따라서 다른
oid다. 키에는 **NFC**를 요구한다.

**값에는 요구하지 않는다.** 사용자 텍스트를 조용히 고치는 것이 더 나쁘다.

### 3-4. lone surrogate 금지

짝이 없는 surrogate는 유효한 텍스트에서 나올 수 없고, `JSON.stringify`의 처리가 런타임마다
달랐다. 키와 값 모두에서 거부한다.

## 4. 왜 이것이 제약이 아니라 기술인가

부분집합을 도입할 때 기존 히스토리를 실측했다:

| 대상 | 객체 | 스칼라 필드 | 위반 |
|---|---|---|---|
| 로컬 저장소 2개 (JSON+CBOR 모두 디코드) | 15,680 | 1,079,410 | 0 |
| hub 객체 평면 1개 (와이어 JSON) | 14,073 | 1,048,085 | 0 |

여섯 검사(비정수·범위초과·astral 키·비NFC 키·lone surrogate·비ASCII 키) 전부 0이다. 즉 이
부분집합은 **현재 상태를 그대로 기술한다.**

측정하지 못한 것도 적는다: 같은 평면의 다른 저장소 4개(총 4,850 객체)는 측정 키가 멤버가
아니어서 401로 접근할 수 없었다.

## 5. 강제 지점

검사는 **`ObjectStore.put`** 하나에 있다. 저자화 API마다 두지 않은 이유는 그것이 우회 있는
검사이기 때문이다 — `put`은 모든 객체가 지나는 유일한 관문이다(저자화·pull·importBundle·
importObjects·hub push).

특히 중요한 자리: `custom:<name>` evidence는 `Checkpoint.evidence`의 **객체 키**가 된다. 즉
사용자가 이름 지은 문자열이 해시 대상의 키다. 위반은 evidence를 붙일 때가 아니라 **그 evidence를
담은 checkpoint를 저장할 때** 걸린다 — `kind`는 `Evidence` 객체 안에서는 값이고, 키가 되는 곳은
체크포인트 조립이다.

## 6. 골든 벡터

`spec/canonical-vectors.json`에 허용 10건·거부 4건이 있다. 각 벡터는 페이로드와 기대 정규 문자열,
기대 oid를 담는다. 다른 언어 구현은 이 파일을 읽어 자기 정규화를 검증한다.

`test/canonical-golden.test.ts`가 이 파일을 **검증한다**(생성하지 않는다). 생성하면 구현이 바뀔 때
벡터가 함께 따라가 아무것도 고정하지 못한다.

**벡터 파일의 두 함정** — 둘 다 실제로 걸렸다:

1. **유니코드 리터럴은 도구가 고친다.** `nfd-key` 벡터를 `café`로 리터럴 입력했더니 편집기/셸이
   NFC로 정규화해 그 벡터가 아무것도 재지 못했다. `́` 이스케이프로 적어야 한다.
   테스트가 "거부 벡터가 주장하는 형태를 실제로 갖는지" 검사한다.
2. **lone surrogate는 파일에 담을 수 없다.** 정의상 유효한 UTF-8이 아니므로 UTF-8 파일이 그것을
   표현하지 못한다(Python이 쓰기를 거부해 파일이 0바이트가 되는 것을 실측했다). 그 케이스는
   벡터 파일이 아니라 **테스트 코드**에서 만든다. 다른 언어 구현도 같은 제약을 만난다.
