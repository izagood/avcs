# 26 — Hub 프로토콜

avcs 클라이언트가 서버와 말하는 규약. **발명이 아니라 기록이다** — 참조 구현(`startHub`)과
독립 구현 하나가 이미 합의한 것을 적었다.

전제: 정규화와 oid 규칙은 `docs/24-canonical-interop.md` 가 정본이다. 이 문서는 그 위의 전송을
다룬다.

## 0. 최소 서버는 엔드포인트 3개다

클라이언트가 **없으면 실패하는** 것은 셋뿐이다.

```
GET  /have            보유 oid 전량
GET  /objects/:oid    객체 하나
POST /objects         객체 하나
```

나머지 아홉은 전부 선택이다. 클라이언트는 능력 광고(`GET /version`)를 보고, 광고가 없거나
엔드포인트가 `404`·`405`·`501` 을 주면 **스스로 예전 경로로 내려간다**. 이것이 설계 의도다 —
클라이언트 주석의 표현대로, avcs 는 "자기가 통제하지 않는 배포"를 상대하는 공개 클라이언트다.

**서버가 부분 구현이어도 1급 시민이다.** 읽기 전용 미러라면 `POST /objects` 없이 두 개만
서빙해도 클론이 된다.

## 1. 주소 공간

프로토콜 경로는 서버가 정하는 접두사 뒤에 온다.

```
참조 구현     http://host:4000/have              (저장소 하나 = 서버 하나)
멀티테넌트    https://host/<org>/<repo>/have     (접두사가 저장소를 고른다)
```

클라이언트는 remote URL 을 그대로 접두사로 쓴다. 즉 `https://host/acme/web` 을 remote 로
등록하면 `https://host/acme/web/have` 를 부른다. **서버는 접두사를 자유롭게 정한다.**

## 2. 인코딩

- 와이어는 **JSON** 이다. 요청·응답 모두.
- **저장은 자유다.** 참조 구현은 정규 CBOR 로 저장하지만 oid 는 정규 JSON 파생이고 와이어도
  JSON 이다. 이 분리가 의도된 것이다 — 저장을 바꿔도 oid 가 안 바뀐다.
- 객체는 `oid` 필드를 **포함해서** 오간다. 받는 쪽은 그것을 신뢰하지 않고 내용에서 다시
  계산한다(§7).

## 3. 능력 협상 — `GET /version`

```json
{
  "name": "avcs-hub",
  "protocol": 5,
  "materializer": "avcs-text3/0.3.0",
  "gated": false,
  "auth": "none",
  "integrate": true,
  "integratePreview": false,
  "events": true,
  "batch": true,
  "batchMaxBytes": 8388608
}
```

| 필드 | 뜻 | 없거나 false 면 |
|---|---|---|
| `name` | 구현 이름. 진단용이고 클라이언트 동작을 바꾸지 않는다 | — |
| `protocol` | 프로토콜 버전(현재 **5**) | — |
| `gated` | 이 서버가 **비멤버의 푸시를 격리**하는가. 객체 수준 권한이고 `auth`(전송 수준)와 다르다 | 열린 서버 — 누구의 푸시든 받는다 |
| `materializer` | 환원기 버전 — 같은 연산 집합이 같은 트리를 내는지의 근거 | — |
| `auth` | `"required"` 면 쓰기에 서명이 필요하다 | 클라이언트가 서명 없이 시도 |
| `integrate` | 통합 큐를 서빙한다 | `POST /finalize` 로 폴백 |
| `events` | 라이브 롱폴을 서빙한다 | 주기 폴링 |
| `batch` | 배치 전송을 서빙한다 | 객체당 요청 1회 |
| `batchMaxBytes` | 이 서버가 받는 최대 본문 | 클라이언트가 `413` 으로 발견 |

`/version` 자체가 없어도 된다. 그때 클라이언트는 **모든 능력을 off 로 가정**한다.

> `batchMaxBytes` 를 광고하는 이유: 없으면 클라이언트가 한계를 `413` 으로 발견해야 하고, 그건
> 실패를 통해 배우는 것이다. 광고하면 처음부터 맞는 크기로 자른다.

## 4. 객체 평면

### 4-1. `GET /have` — 필수

응답은 **oid 문자열 배열**이다(객체가 아니다).

```json
["operation_ab12…", "checkpoint_cd34…", "blob_ef56…"]
```

푸시 협상(클라이언트가 보낼 것을 고른다)과 풀 발견(받을 것을 고른다) 양쪽에 쓰인다.

### 4-2. `GET /sync?since=N` — 선택

`/have` 의 증분판. 객체 로그의 인덱스 `N` **이후**에 추가된 oid 와 새 커서를 준다.

```json
{ "oids": ["operation_ab12…"], "cursor": 1841 }
```

- `since=0`, 또는 범위를 벗어난 값이면 전량과 현재 커서를 준다.
- 커서는 **추가 순서의 인덱스**다. 서버는 객체 로그를 재정렬하지 않아야 한다.
- **정확성이 커서에 의존하지 않는다.** 잘못된 커서는 최악의 경우 더 많이 전송할 뿐이다.
  그래서 커서를 못 지키는 서버는 이 엔드포인트를 안 서빙하면 된다.

### 4-3. `GET /objects/:oid` — 필수

객체 JSON, 없으면 `404`. `404` 는 정상 응답이다 — 클라이언트는 축출 경쟁으로 보고 건너뛴다.

### 4-4. `POST /objects` — 필수

본문이 객체 하나. 응답:

| 상태 | 본문 | 뜻 |
|---|---|---|
| `200` | `{ "oid": "operation_ab12…" }` | 저장됐다(또는 이미 있었다) |
| `400` | `{ "error": "…" }` | 형식이 틀렸다 |
| `401` | `{ "error": "…" }` | 서명이 없거나 유효하지 않다 |
| `403` | `{ "error": "…" }` | 서명은 유효하나 권한이 없다 |
| `413` | `{ "error": "…" }` | 본문이 너무 크다 |
| `429` | `{ "error": "…" }` + `retry-after` | 스로틀 |

`200` 은 **멱등**이다. 같은 객체를 다시 보내면 같은 oid 로 `200` 이다 — 내용주소이므로.

### 4-5. `POST /objects/batch` — 선택

```json
{ "objects": [ {…}, {…} ] }
```

응답은 **객체마다 판정**을 준다. 하나가 거부돼도 나머지는 저장된다.

```json
{ "results": [
  { "oid": "operation_ab12…", "status": "stored" },
  { "oid": "operation_cd34…", "status": "rejected", "reason": "…" }
] }
```

`400` 은 `{ objects: [...] }` 형태가 아닐 때, `413` 은 개수·크기 한계를 넘을 때다.

### 4-6. `POST /objects/fetch` — 선택

```json
{ "oids": ["operation_ab12…", "operation_cd34…"] }
```

```json
{ "objects": [ {…}, {…} ], "truncated": false }
```

- 없는 oid 는 **조용히 빠진다**(에러가 아니다).
- `truncated: true` 면 응답 크기 한계에 걸린 것이다. 클라이언트는 **아직 안 온 것만** 다시
  묻고, 진전이 없으면 멈춘다. 서버는 매 응답에 **최소 하나**를 담아야 한다 — 그러지 않으면
  클라이언트가 진전 없음으로 판단하고 포기한다.

## 5. 거버넌스 평면

### `GET /refs` — 선택

```json
{ "refs": { "policy": "policy_ab…", "member:human:h": "membership_cd…", "head:main": "checkpoint_ef…" } }
```

클라이언트는 **접두사가 맞는 것만** 채택한다: `policy`, `member:`, `protection:`, `head:`.
작업 ref(`view:*`, `checkpoint:*`)는 로컬에 남는다.

그리고 **가리키는 객체를 이미 들고 있을 때만** 채택한다. 이 조건이 중요하다 — 없는 주소를
가리키는 ref 를 채택하면 그것을 읽는 게이트가 실패하고, 그 실패가 정책 판정의 얼굴을 하고
나온다.

## 6. 판정 평면

### 6-1. `POST /finalize` — 선택

head 를 CAS 로 전진시킨다. 옛 경로이고, `integrate` 를 서빙하지 않는 서버가 이것만 둔다.

```json
{ "view": "main", "newCheckpoint": "checkpoint_ab…", "parentHead": "checkpoint_cd…", "by": "human:h", "sig": "…" }
```

| 상태 | 뜻 |
|---|---|
| `200` | 전진했다 |
| `403` | 서명이 주장하는 멤버의 것이 아니다 |
| `409` | head 가 그 사이 움직였다 (CAS 실패) |
| `422` | 정책이 거부했다 |

`parentHead` 는 생략 가능하고, 그때는 CAS 없이 전진한다.

### 6-2. `POST /integrate` — 선택

통합 큐. 판정 다섯 종이 있고 **상태 코드가 판정을 나른다**.

```json
{ "view": "main", "checkpoint": "checkpoint_ab…", "by": "human:h", "ticketId": "…", "sig": "…" }
```

| 판정 | 상태 | 뜻 |
|---|---|---|
| `advanced` | `200` | 랜딩했다. `head` 를 함께 준다 |
| `queued` | `202` | 다른 티켓이 진행 중이다. **같은 티켓으로 재시도**하라 |
| `conflict` | `409` | 충돌. 수리 패킷을 함께 준다 |
| `needs_evidence` | `428` | 요구된 검사의 증거가 필요하다. 검증할 트리 해시를 준다 |
| `rejected` | `422` | 정책이 거부했다 |

**`queued` 는 "pull 해서 다시 하라" 가 아니다.** 연산은 append-only 이므로 같은 티켓을
재제출하면 새 head 위로 다시 환원된다. 클라이언트에게 로컬 히스토리를 버리라고 요구하는
판정은 이 프로토콜에 없다.

`ticketId` 는 **멱등 키**다. 같은 티켓으로 다시 제출하면 서버는 이전 판정을 재생한다 —
네트워크 재시도·에이전트 재시도·잡 재실행이 전부 이 경로로 온다.

### 6-3. `GET /events?since=N&timeoutMs=M` — 선택

라이브 수렴 롱폴. `since` 는 `/sync` 와 **같은 커서**다(의미가 하나다).

- 커서 이후 새 oid 가 있으면 즉시 응답.
- 따라잡았으면 변화가 있을 때까지 파킹, 타임아웃이면 빈 목록으로 하트비트.
- 응답은 **매번 거버넌스 ref 전체**를 함께 담는다 — 객체가 추가되지 않아도 head 전진이
  보이게.

## 7. 인증

SSH 를 그대로 옮긴 모양이다. 비밀이 전송되지 않는다.

```
~/.ssh/id_ed25519   →  로컬 액터의 개인키
authorized_keys     →  서버의 member:<keyId> → Membership.publicKey
challenge-response  →  요청 자체에 대한 서명
```

헤더:

```
Authorization: AVCS-Sig keyId="human:h", ts="2026-08-31T08:00:00.000Z",
               nonce="<base64url>", sig="<base64>", scope="/acme/web", bsig="<base64>"
```

서명 대상(정규 요청):

```
METHOD \n path \n ts \n nonce \n sha256hex(body) [\n scope]
```

- `path` 는 **서버 접두사를 뺀** 프로토콜 경로다(`/objects/fetch`, `/have`).
- `body` 는 보낼 본문 그대로. 없으면 빈 문자열의 sha256.
- ed25519 서명이고 `signMessage`/`verifyMessage` 가 정본이다.

**서명이 둘인 이유.** `sig` 는 scope 없는 재료를 덮고, `bsig` 는 scope 를 포함한 재료를 덮는다.
하나로 합치면 배포된 검증자 전부가 모든 요청을 거부한다 — 실제로 첫 시도에서 그렇게 됐다.
scope 를 **요구하는** 서버는 `bsig` 를 검사하고, 옛 서버는 `sig` 만 보고 계속 동작한다.

신선도: `ts` 가 서버 시계와 기본 5분 이상 벌어지면 거부. `nonce` 는 창 안에서 재사용 금지.

읽기 서명은 **가산적**이다. 서명이 없으면 헤더가 없고, 읽기가 공개인 서버는 무시한다.

## 8. 객체를 신뢰하지 않는 방법

받은 객체의 `oid` 필드를 **믿지 않는다.** 내용에서 다시 계산하고, 계산된 주소에 저장한다.

거부가 아니라 **재계산**이라는 점이 중요하다. 거부는 판단이 필요하고 판단은 틀릴 수 있지만,
주소를 내용에서 다시 계산하는 것은 판단이 없다. 변조된 객체는 **자기 oid 에 착지**하고 원본
자리를 뺏지 못한다. 참조 구현의 주석 표현대로 — "lands it at its own oid rather than poisoning
ours."

그래서 서버는 입구마다 검증을 다시 쓸 필요가 없다. content-addressing 이 그 자체로 방어다.

## 9. 프로토콜 버전

`protocol` 은 정수 하나이고 현재 **5** 다.

- **능력을 더하는 변경은 버전을 올리지 않는다.** `GET /version` 의 플래그로 광고하고, 모르는
  클라이언트는 폴백한다. 배치 전송(`batch`)이 그렇게 들어왔다.
- 버전을 올리는 것은 **기존 계약의 의미가 바뀔 때**다. 그때도 서버는 옛 의미를 계속 서빙할
  수 있어야 한다.
- 클라이언트는 자기가 모르는 더 높은 버전을 봤을 때 **거부하지 않는다** — 아는 능력만 쓴다.

## 10. 서버를 만들 때 흔히 틀리는 것

| | 증상 |
|---|---|
| 키 정렬을 "알파벳 순" 으로 | `A` 와 `a` 가 뒤집혀 oid 가 갈린다. 코드포인트 순이다(`docs/24`) |
| 비-ASCII 값을 `\uXXXX` 로 이스케이프 | 바이트가 달라 oid 가 갈린다. UTF-8 그대로 둔다 |
| 없는 oid 에 `404` 대신 에러 | 클라이언트가 축출 경쟁으로 보고 넘어가지 못한다 |
| `truncated` 응답에 아무것도 담지 않음 | 클라이언트가 진전 없음으로 판단하고 포기한다 |
| `/refs` 에서 없는 객체를 가리키는 ref 를 노출 | 그것을 읽는 게이트가 실패하고, 정책 판정처럼 보인다 |
| `queued` 를 "클라이언트가 pull 해야 함" 으로 해석 | 재제출이 정상 경로다. 로컬 히스토리를 버리게 하는 판정은 없다 |
| `ticketId` 를 무시 | 재시도가 중복 랜딩이 된다 |

## 11. 적합성

명세는 읽고 오해할 수 있다. 오해를 실패로 바꾸는 것은 적합성 스위트다 — 3단계에서 만든다.
그때까지 이 문서와 `spec/canonical-vectors.json` 이 계약이다.
